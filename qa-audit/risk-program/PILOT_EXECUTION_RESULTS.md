## What was connected

One real HTTP booking lifecycle created a future customer draft with note/address, added a sale item and hold, submitted it to vendor review, retried the identical submit without persisted effects, and accepted the final vendor contribution. tester.army signed in and verified the resulting account page showed Confirmed, the exact service and note, and the total. These were API mutations followed by browser readback, not a complete UI checkout.

Financial fixtures separately followed real HTTP capture → committed paid booking/ledger → real full refund processor → refunded booking/ledger, with gateway boundary substitution. They were not the same booking as the browser lifecycle; no single storefront-to-gateway journey is claimed. All exact amount/currency/missing-amount mismatch branches preserved pending/unpaid rows and emitted no capture event on MariaDB.
