# Issue #51 — source review, runtime validation deferred

The historical report compares zero pending approvals on the operations dashboard with a queue total of thirteen. Those numbers are historical observations, not freshly reproduced results.

The source confirms a permission mismatch. `VendorProfilePolicy::viewAny()` uses `view_any_vendor::profile`, while the operations section, `AdminDashboardSectionsWidget::operationsData()` vendor count gate, and `PendingVendorApprovalsWidget::canView()` used `view_any_vendor_profile`. A viewer authorized by the actual vendor-profile policy could therefore have the operations section hidden and the pending-vendor count forced to zero before its query ran. The query itself is consistent: it filters `approval_status` by `ApprovalStatus::Pending->value`, which is `pending`; the operations metric and attention metric both use that computed count.

The operations section now delegates its vendor gate to `VendorProfileResource::canViewAny()`, and the pending-approvals widget uses the policy's canonical ability. Source review of the same dashboard also found stale gates for bookings, modifications, interventions, notifications and withdrawals; those metrics now use their target resources' `canViewAny()` checks. The operations chart includes only series whose resources are readable.

The financial section previously loaded every financial aggregate when any one finance permission matched. It now scopes payment, refund, commission and withdrawal queries, chart series, summaries and attention counts to their owning resource access. Net revenue requires both payment and refund access. The payout panel and its link are shown only to withdrawal viewers, and it displays the withdrawal payable amount. Both dashboard caches vary by user and their individual resource visibility bits, including homepage-package access. The header widget's vendor, booking-monitor, payment and wallet-ledger counts use their target resources' access checks. The wallet metric is owned by `WalletLedgerViewerResource` and `WalletPolicy`; the sections widget has no wallet-specific aggregate, so wallet access does not expose unrelated finance data.

The historical queue total of thirteen is not freshly reproduced, so same-viewer/same-dataset runtime acceptance remains deferred. Pre-edit widget sources are retained in `.e2e/risk-program/remediation/github51-preedit-AdminDashboardSectionsWidget.php` and `.e2e/risk-program/remediation/github51-preedit-PendingVendorApprovalsWidget.php`; the permission follow-up snapshots are in `.e2e/risk-program/remediation/` with the `github51-permission-followup-preedit-` prefix. No data, roles, production configuration or permission definitions were changed; no tests or checks were run.
